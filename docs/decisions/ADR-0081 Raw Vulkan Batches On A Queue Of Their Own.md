# ADR-0081: Raw Vulkan batches on a queue of their own in wgpu's queue family

> Amended by ADR-0088: on a one-queue GPU in a window the default draws the eyes inside the viewer frame instead of refusing; only `--decoupled-render` keeps the refusal.

## Context

Vulkan requires `vkQueueSubmit`, `vkQueueWaitIdle` and `vkQueuePresentKHR` on one `VkQueue` to be externally synchronized ([VKQ]), and `vkDeviceWaitIdle` to be synchronized with every queue of the device ([VKX] L14879-14880). wgpu-core serializes its own submits and presents under the device's `command_indices` lock ([WGC] `queue.rs` L1600-1740, `present.rs` L355-356); raw calls on the same queue must be serialized by us. The QAROS Vulkan path (ADR-0029) makes three kinds of raw calls, all on wgpu's queue: the handover's acquire and release batches, the empty batch that signals a discarded frame's semaphore (`submit_sync_batch`), and a `vkQueueWaitIdle` before a sender goes. It also stages a wait and a signal semaphore on wgpu's queue, which wgpu-hal attaches to whichever submission it makes next, from any thread ([WGH] `mod.rs` L1420-1428, L1524-1566).

QAROS submits nothing on our device: it imports the sender images into a device of its own and submits there ([QVV] L651-659; `QarStreamParamsVulkan` carries only the physical device and the device, [HDR]), which is why images are released to `VK_QUEUE_FAMILY_EXTERNAL`. The only other submitters on our queue are wgpu's users in this process.

ADR-0061 serializes them with `re_renderer::queue_submission_lock()`, and rejected a second queue because wgpu exposes one per device; that still holds for wgpu's own work, and this ADR amends ADR-0061 by giving our raw work a queue wgpu never sees. eframe's window path submits and presents without it (egui-wgpu 0.37.0 `winit.rs`, `queue.submit` L757-762, `queue.present` L789-792), so `--decoupled-render` with the QAROS Vulkan sink is refused in a window: a raw batch on the render thread could overlap eframe's `vkQueueSubmit`, and eframe's submission could take the semaphores the render thread staged.

wgpu-hal 30 opens the device with one queue create info for family 0 and takes queue index 0 of it ([WGA] L3005-3008, L3063-3064). Its device creation callback may modify the queue create infos ([WGH] L1712); wgpu-hal passes the vector to `vkCreateDevice` after the callback returns and reads nothing else from it ([WGA] L3014-3032).

## Decision

- **A second queue in wgpu's family.** `VulkanDevice::create` asks, through the callback it already passes to `open_with_callback`, for two queues in the family of wgpu's create info when that family's `queueCount` is at least 2. wgpu keeps queue 0; queue 1 is fetched with `vkGetDeviceQueue` and wrapped as `RawQueue`. Both queues get priority 1.0, from a `static` array, since the pointer must outlive the callback until `vkCreateDevice`. Should wgpu ever take queue 1 itself, `VulkanDevice::create` returns an error instead of sharing it.
- **Every raw call goes to `RawQueue`.** The handover's acquire and release batches, `submit_sync_batch` and `wait_queue_idle` take a `RawQueue` and submit under its own mutex, so raw calls are synchronized with each other whatever the thread. The same family means no ownership transfer between the two queues; the images' acquire from and release to `VK_QUEUE_FAMILY_EXTERNAL` stay as they are.
- **Staged semaphores are robust to another thread's submission.** The handover stages its wait (on the acquire batch's semaphore) before its wgpu submission, and stages its signal (the semaphore the release batch waits on) only after that submission returns, then flushes it with an empty `queue.submit`. Whichever wgpu submission takes them, the order holds: a signal taken by any submission after ours covers ours, since a signal's first scope includes every command earlier in submission order on the queue; a wait taken by a submission before ours still orders ours, since a wait's second scope includes every command later in submission order ([VKS]). The release batch is submitted after the flush returns, so its wait has its signal submitted. A wgpu submission can end before the driver (a lost device, [WGC] L1604-1606); the handover then finds its signal still staged, takes the signal and the wait back off wgpu's lists, skips the release batch and stops for good.
- **One-queue fallback.** When the family has a single queue (MoltenVK on the Mac, the Intel iGPU on the Legion), `RawQueue` is wgpu's queue 0 and `RawQueue::shares_wgpu_queue` is true. Everything stays as ADR-0061 has it: the QAROS Vulkan sink reports `GpuFrameSink::submits_raw_to_wgpu_queue`, the render thread holds the queue submission lock around its sink calls, and `--decoupled-render` with the Vulkan sink in a window is refused. The refusal moves from option parsing to sink creation (`qaros_setup::vulkan_sink`), the first point where the device exists: the viewer has then already joined the session and leaves it with the error, before any sender exists. A device not made by `VulkanDevice::create` (Rerun's own) gets the fallback too.
- **A window resize parks the render thread.** eframe reconfigures the window's surface inside its `Resized` handler, with nothing of the app's running first (eframe 0.37.0 `wgpu_integration.rs` L997-1018), and on Windows paints there too (`run.rs` L123-134, [EFW]). wgpu-core's `Surface::configure` waits for wgpu's last submission and then fails with `GpuWaitTimeout` ("Failed to wait for GPU to come idle") when the queue is not empty, which only another thread's submission can cause ([WGR]); the render thread's eye submits and handover flushes are such submissions. When the wait passes, wgpu-hal calls `vkDeviceWaitIdle` outside `command_indices` ([WGI], [WGS]), beside whatever the render thread calls on queue 0 or queue 1. So with `--decoupled-render` in a window, eframe's application runs on an event loop of ours (`eframe::create_native` and `run_app_on_demand`, as `eframe::run_native` does with Rerun's options), and our handler wraps each `Resized` event: it asks the render thread to park between two eye frames, waits until it has (at most 500 ms, then it warns once and goes ahead), lets eframe handle the event, and releases it. Between eye frames the render thread has no wgpu submit and no raw call running, so the configure's wait sees only finished work and `vkDeviceWaitIdle` runs alone. A request also ends the render thread's idle wait, so it parks within one eye frame. The eyes pause for the configure and the window's repaint.
- **The queue submission lock stays in the patched `re_renderer`, needed only on the fallback.** With two queues the sink's calls do not take it; Rerun's `before_submit`, the eye submit and the panel capture still take it, so those wgpu submits still wait for each other briefly, but never for a sink call. Removing it would mean refusing `--decoupled-render` with the Vulkan sink on every one-queue device, headless too, which loses the Mac development path for that mode; keeping it costs the existing lines of the patch.
- **Tests.** The handover and sync-batch tests run on whichever `RawQueue` the device offers, and again on the fallback forced through `VulkanDeviceConfig::separate_raw_queue`. With two queues, another thread submits to wgpu's queue throughout every handover, and the consumer checks each frame's pixels. A test lets an unrelated wgpu submission take a staged wait and checks the work still waits for the raw batch before it. The device test checks queue 1 of wgpu's family where the family has two queues; the sink-creation check is unit-tested for both queue kinds. The render thread's eye frame loop is unit-tested for the pause: a request ends its idle wait and parks it, neither a wake nor a new scene runs a frame while parked, the next frame runs once the pause ends, a stop ends a pause, and a pause after the loop ended does not wait. The two-queue path runs on Windows with NVIDIA (family 0 has 16 queues on the Legion's RTX 5070 Laptop GPU, [VKI]); MoltenVK has one queue per family ([VKI]), so the Mac runs the fallback only. The windowed run on the Legion, with window resizes, is the end-to-end check, with `VK_LAYER_KHRONOS_validation` when it is diagnosed.

## Alternatives considered

- **B: vendor egui-wgpu and take the lock around eframe's submit and present.** A third vendored crate, and the lock would have to live in a crate both see (egui-wgpu does not depend on `re_renderer`). The clean form is an upstream hook in egui-wgpu around submit and present; worth asking for, not worth carrying.
- **C: record our barriers inside wgpu's command buffer through hal access.** wgpu inserts its own layout transitions ahead of an encoder's commands at submit, so the acquire barrier would run after wgpu's first use of the image (`handover.rs` module doc).
- **`VK_KHR_internally_synchronized_queues` for the resize.** The Legion's NVIDIA driver offers it ([VKI]), and `vkDeviceWaitIdle` does not need external synchronization with queues created with `VK_DEVICE_QUEUE_CREATE_INTERNALLY_SYNCHRONIZED_BIT_KHR` ([VKX] L14876-14886); the device callback could set the flag on wgpu's queue create info and enable the extension and its feature. It leaves wgpu-core's `GpuWaitTimeout` as it is, since that is wgpu's own check that no other thread submitted during the configure's wait, so the render thread has to stop for the configure anyway, and then `vkDeviceWaitIdle` already runs alone. MoltenVK and the Intel iGPU would need the fallback regardless.
- **Living with the failed configure.** egui-wgpu retries the configure on a later frame, but each failed one leaves the swapchain at the old size while egui records at the new one (`set_scissor_rect` outside the render target, so that frame's submission is rejected), and a configure that succeeds still runs `vkDeviceWaitIdle` beside the render thread.
- **Raw batches on a queue of another family** (a transfer-only family). Each frame would then need ownership transfers between our families on top of those with `VK_QUEUE_FAMILY_EXTERNAL`; the graphics family has queues to spare where it matters.

## Consequences

- Positive: `--decoupled-render` with the QAROS Vulkan sink runs in a window on devices whose graphics family has two queues, and the render thread's sink calls no longer hold up the UI thread's `before_submit`.
- Negative: one extra empty wgpu submission per handover (per user and frame). A UI submission that lands between ours and the flush delays that frame's release by its own GPU time.
- Negative: the resize hook covers the reconfigure in eframe's `Resized` handler, which is where a resize reconfigures. egui-wgpu also reconfigures while painting, after a suboptimal or outdated surface texture, and recreates a lost surface there ([EGW]); those paths run beside the render thread as before, and the configure can fail there with `GpuWaitTimeout` and be retried on the next frame. Dropping wgpu's queue calls `vkQueueWaitIdle` on queue 0 outside `command_indices` ([WGC] L281), unsynchronized with the render thread in the same way.
- Negative: eframe keeps an error that ends its event loop to itself when it runs on an event loop of ours; it logs it, and the viewer reports an app creator that failed or never ran, but an error after the app was created no longer reaches `main`'s exit code.
- Negative: in a window the desktop still draws Rerun's 3D view every frame, so the window costs GPU time beside the eyes; this fixes correctness, not that cost.
- Negative: on one-queue devices nothing changes: the lock and the window refusal remain. On a wgpu upgrade, re-check that wgpu-hal still takes queue 0 of the first create info and passes the callback's create infos to `vkCreateDevice`.
